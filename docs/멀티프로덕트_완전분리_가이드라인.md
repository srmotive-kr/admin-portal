# Admin Portal 멀티프로덕트 완전 분리 가이드라인 (2026-08-14)

## 0. 원칙

**콤보박스(`ProductContext`)에서 상품을 선택하는 행위는 "필터를 바꾸는 것"이
아니라 "작업 공간을 전환하는 것"이다.** Smart HR+를 선택했을 때와 Smart
Planner+를 선택했을 때는 같은 화면에 다른 데이터가 보이는 게 아니라, **화면
구성 자체가 달라야 한다.** 이 문서는 이 원칙 하나를 기준으로 현재 상태를
점검하고 구현 방향을 정한 것이다 — "이 정도만 해도 되지 않을까"를 검토하는
문서가 아니라, 이 원칙을 만족시키기 위해 무엇을 고쳐야 하는지를 정리한
실행 계획이다.

이 원칙에서 파생되는 두 가지 하위 규칙:

- **데이터는 상품 간에 물리적으로 섞일 수 없다.** 필터가 우연히 빠지거나
  `productCode`가 일시적으로 비어있는 순간에도, "전체 노출"이라는 결과가
  나오는 코드 경로는 전부 버그다.
- **메뉴 구성 자체가 상품마다 다르다.** 한 상품에만 의미 있는 메뉴가 다른
  상품을 선택했을 때 보이거나(내용 무관하게 노출), 접근 가능한 상태로
  남아있으면 안 된다.

**(2026-08-14 추가 결정)** "데이터가 섞이지 않는다"를 지키는 방법으로 처음엔
공유 테이블 + `product_code` 필터를 썼는데, 이건 **RLS로 원천 차단이 안 된다는
구조적 한계**가 있다는 게 드러났다 — smart-hr-plus와 Smart Planner+가 같은
Supabase 프로젝트의 같은 anon 키를 쓰기 때문에, DB는 "누가 물어보는지"를
구분할 방법이 없고 클라이언트가 요청에 실어보내는 `product_code` 값을
그대로 신뢰하는 것 말고는 막을 방법이 없었다. 그래서 원칙을 한 단계 더
강화한다: **가능한 곳은 공유 테이블+필터가 아니라 상품별로 물리적으로 분리된
테이블을 쓴다.** 필터를 빠뜨리는 실수 자체가 구조적으로 불가능해진다(다른
상품 데이터가 애초에 그 테이블에 없으므로). §5(공지 관리)와 Seed 편집기의
`seed_codes`(→ `seed_codes_smart_hr_plus`)에 이미 적용했다.

## 1. 메뉴를 두 종류로 나눈다

### A. 공용 인프라 메뉴 — 화면 구조는 공유, 데이터는 완전 분리
라이선스 관리, 릴리즈 관리, 이메일 발송 이력, FREE 갱신 관리, 대시보드.
"제품 기능"이 아니라 **어떤 제품이든 필요한 라이선스·배포 인프라**이므로
화면 자체를 상품별로 따로 만들지 않는다. 대신 상품이 바뀌면 그 안의 데이터는
1건도 겹치지 않아야 한다 — 이게 지켜지지 않으면 "완전 분리"가 아니다.

### B. 제품 도메인 메뉴 — 화면 자체가 상품 전용
연간 관리 항목, 공지 관리, Seed 편집기. 인사·급여라는 Smart HR+ 업무
도메인에 종속된 콘텐츠라, 상품이 바뀌면 **다른 상품의 화면이 남아있으면
안 된다.** Smart Planner+ 전용 콘텐츠가 아직 없다면 "없음"으로 완전히
비우는 것이 맞다 — Smart HR+ 콘텐츠를 그대로 보여주는 건 어떤 경우에도
허용되지 않는다.

## 2. 메뉴별 현재 상태 — 원칙 위반 지점 (코드로 확인한 사실)

### 2.1 공용 인프라 메뉴(A그룹) — 데이터 분리 위반

| 메뉴 | 파일 | 위반 내용 |
|---|---|---|
| 라이선스 관리 | `LicenseManager.jsx` | `if (productCode) q.eq(...)` — productCode가 비면 필터 없이 **전체 노출** |
| 릴리즈 관리 | `ReleaseManager.jsx` | 동일 |
| 이메일 발송 이력 | `EmailHistory.jsx` | 동일 |
| FREE 갱신 관리 | `FreeRenewal.jsx` | 동일 |
| 대시보드 | `Dashboard.jsx` | `scope = q => productCode ? q.eq(...) : q` — 동일한 패턴 |

다섯 화면 전부 "productCode가 있으면 필터"가 아니라 **"productCode가
없으면 아무것도 안 보여준다"**로 바꾼다. 필터 누락이 "전체 노출"로 이어지는
경로를 코드에서 없앤다(fail-safe: 조건이 불확실하면 빈 화면, 안전한 쪽으로).

### 2.2 제품 도메인 메뉴(B그룹) — 메뉴 분리 위반

| 메뉴 | 파일 | 위반 내용 |
|---|---|---|
| Seed 편집기 | `SeedEditor.jsx` | `Layout.jsx`에서 `productOnly: 'smart-hr-plus'`로 이미 완전히 숨겨짐. 뒷단 테이블도 `seed_codes` → **`seed_codes_smart_hr_plus`로 물리적 분리 완료**(2026-08-14) — 원칙을 만족하는 메뉴 |
| 연간 관리 항목 | `ChecklistPage.jsx` | 상품 개념이 없다. 하드코딩된 `SECTIONS`가 전부 4대보험·최저임금·연말정산 등 인사급여 전용 내용이고, Smart Planner+를 선택해도 **그대로 노출된다.** (§3에서 사이드바 자체는 이미 제외 — 화면 코드 정리는 §6-3 참고) |
| 공지 관리 | `BroadcastManager.jsx` | ~~`broadcast_messages` 테이블이 live DB에 존재하지 않았음~~ → **`broadcast_messages_smart_hr_plus` / `broadcast_messages_smart_planner_plus` 두 개의 물리적으로 분리된 테이블로 신규 구축 완료**(2026-08-14, §5) |

## 3. 사이드바 메뉴 구성을 상품별로 분리한다

`Layout.jsx`의 `NAV`는 지금 하나의 배열에 `productOnly` 예외 플래그 하나만
얹은 구조다. 원칙에 맞게 뒤집는다 — **기본을 상품별 메뉴 세트로 정의**하고,
공용 인프라 메뉴만 공통으로 포함시킨다:

```js
const COMMON_NAV = [
  { to: '/', label: '대시보드', icon: '◈' },
  { to: '/licenses', label: '라이선스 관리', icon: '🔑' },
  { to: '/releases', label: '릴리즈 관리', icon: '📦' },
  { to: '/email-history', label: '이메일 발송 이력', icon: '📧' },
  { to: '/renewals', label: 'FREE 갱신 관리', icon: '♻️' },
]

const NAV_BY_PRODUCT = {
  'smart-hr-plus': [
    ...COMMON_NAV,
    { to: '/seed', label: 'Seed 편집기', icon: '🗄️' },
    { to: '/checklist', label: '연간 관리 항목', icon: '📋' },
    { to: '/broadcast', label: '공지 관리', icon: '📢' },
  ],
  'smart-planner-plus': [
    ...COMMON_NAV,
    { to: '/broadcast', label: '공지 관리', icon: '📢' }, // §5 재구축 후 공통 재사용
    // 그 외 Smart Planner+ 전용 도메인 메뉴는 아직 없음 — 없는 채로 둔다(§4)
  ],
}
```

`Layout.jsx`는 `NAV_BY_PRODUCT[productCode] ?? []`로 사이드바를 그린다.
상품을 전환하면 사이드바에 뜨는 메뉴 항목 자체가 물리적으로 바뀐다.

## 4. Smart Planner+ 전용 도메인 메뉴 — 지금은 "없음"이 맞는 상태다

Smart HR+의 B그룹 메뉴(연간 관리 항목)를 복사해서 Smart Planner+에 붙이는
것은 원칙 위반이다 — 내용이 인사급여 전용이라 Smart Planner+에는 그냥
틀린 정보다. **완전 분리 원칙을 지키는 올바른 기본 상태는 "그 메뉴가 아예
없는 것"**이다. 실제 운영 요건(재무설계 관련 매년 갱신 데이터가 있는지 등)이
확인되기 전까지는 §3의 `NAV_BY_PRODUCT['smart-planner-plus']`에 해당 항목을
추가하지 않는다 — Smart HR+ 콘텐츠를 임시로라도 보여주는 타협은 하지 않는다.

## 5. 공지 관리 — 상품별 물리적 분리 테이블로 구축 완료 (2026-08-14)

`broadcast_messages` 테이블 자체가 없어서 신규 구축이었는데, 처음 설계했던
"`product_code` 컬럼을 포함한 공유 테이블 + 필터" 방식은 §0에서 정리한
구조적 한계(RLS로 원천 차단 불가) 때문에 채택하지 않았다. 대신 **상품별로
완전히 별도인 테이블**로 만들었다 — `product_code` 컬럼 자체가 없다(테이블
정체성 자체가 상품을 나타내므로 컬럼으로 중복 표현할 필요가 없다):

```sql
create table broadcast_messages_smart_hr_plus (
  id uuid primary key default gen_random_uuid(),
  title text not null,
  body text not null,
  severity text not null default 'info', -- info | warning | critical
  require_ack boolean not null default false,
  action_label text,
  action_menu text,
  expires_at timestamptz,
  created_at timestamptz not null default now()
);
-- broadcast_messages_smart_planner_plus 도 동일 스키마로 별도 생성
-- 둘 다: RLS enable, authenticated에게 전체 권한 정책, anon에게 SELECT 전용
-- 정책 + 각각 GRANT(anon: SELECT만 / authenticated: 전체) 부여
```

구현 완료된 내용:
- `BroadcastManager.jsx`: `broadcastTable(productCode)` 헬퍼가
  `broadcast_messages_${productCode.replace(/-/g,'_')}`로 테이블명을 계산해
  조회·등록·삭제 전부 그 테이블만 사용(다른 상품 테이블에 접근할 방법 자체가
  코드에 없음).
- 클라이언트(`smart-hr-plus/src/ipc/handlers/broadcast.js`)는
  `broadcast_messages_smart_hr_plus`를 직접 조회 — 필터 파라미터가 아니라
  테이블명 자체가 고정이라 빠뜨릴 수 있는 "필터"가 존재하지 않는다.
- 실제 REST 쿼리로 검증: 두 테이블에 각각 테스트 행을 넣고 smart-hr-plus
  쿼리로 조회하면 자기 테이블의 행만 반환됨을 확인(교차 노출 불가능함을
  구조적으로 증명).
- "이동할 메뉴 키" 힌트 문구는 아직 `productCode === 'smart-hr-plus'`
  조건부로만 하드코딩되어 있다 — Smart Planner+ 쪽 실제 메뉴 키 체계가
  정해지면 `NAV_BY_PRODUCT[productCode]`에서 뽑아오는 방식으로 일반화 필요
  (남은 작업, §6).

## 6. 구현 범위

2. ✅ `Layout.jsx`를 `NAV_BY_PRODUCT` 구조로 전환 (§3)
3. ✅ `ChecklistPage.jsx` 라우트 가드 완료 — `App.jsx`에 `ProductOnlyRoute` 추가,
   `/checklist`는 `productCode === 'smart-hr-plus'`가 아니면 콘텐츠 대신 안내

   되돌리면 정상 콘텐츠 노출.
4. ✅ 공지 관리 — `broadcast_messages_smart_hr_plus` /

5. ✅ `seed_codes` → `seed_codes_smart_hr_plus` 물리적 분리 완료(§2.2) —

   데이터 102건 무손실 확인
6. ✅ Smart Planner+ 전용 B그룹 메뉴 요건 확정·구현 (2026-08-14, 최초 구현 →
   같은 날 재설계) — "재무설계 관련 매년 갱신 데이터가 있는지"가 실제로 확인됨:
   Smart Planner+ 사용자 앱의 환경설정 메뉴·계산엔진이 쓰는 참조 데이터가 해당.
   Supabase에 `planner_*` 8개 테이블 신규 생성(`supabase_planner_reference_data.sql`,
   Smart HR+ 스키마와 무관하게 Smart Planner+ 로컬 SQLite 실제 스키마 그대로 옮김),
   admin-portal에 `PlannerSeedEditor.jsx`(SeedEditor.jsx와 완전히 별도 파일, 서로
   미참조)를 신규 작성해 `/seed` 라우트를 `App.jsx`의 `SeedRoute`가 상품별로 분기.
   `NAV_BY_PRODUCT['smart-planner-plus']`에도 Seed 편집기 메뉴 추가.

   **최초 구현은 화면 구성이 실제 앱과 안 맞고 메뉴가 중복돼서 재설계함**(사용자
   지적): 처음엔 admin이 임의로 지은 8개 탭(코드관리/은퇴생활수준/국민연금
   기준소득월액/국민연금 재평가율/시스템설정/은퇴 기본값/교육 기본값/결혼
   기본값)을 나열했는데, (1) "코드관리"라는 이름이 실제 환경설정의 진짜
   "코드관리"(저축기간 설정, `SavingsTermSettings.jsx`, 완전히 다른 개념)와
   충돌했고, (2) "은퇴생활수준"이 코드그룹 라벨과 별도 탭으로 중복 등장했고,
   (3) "은퇴생활수준"·"은퇴 기본값"이 실제로는 한 화면(`RetireDefaultsTable.jsx`)
   인데 admin에선 둘로 쪼개져 있었다. `EnvironmentTab.jsx`(환경설정 4개 서브메뉴:
   코드관리/기본값관리/적정성기준/RP스크립트관리)를 실제로 전부 재조사해 재설계:

   - **기본값관리**(실제 메뉴 이름 그대로, 시스템값만) — 은퇴/교육/결혼/상승률

     `user_settings`) 쪽은 admin이 관리할 대상이 아니라 처음부터 제외.
   - **참조 데이터**(환경설정에는 없음, 계산엔진·입력폼 드롭다운 전용, 실제
     메뉴와 이름이 겹치지 않게 구분) — "참조코드"(`code_names`, 실제 이름
     "코드관리"와 충돌 방지 위해 개명), 국민연금 기준소득월액, 국민연금
     재평가율, 기타 설정값(`planner_system_config` 중 상승률 3키 제외 나머지 —
     `PENSION_AVG_STD_INCM_MN` 등).
